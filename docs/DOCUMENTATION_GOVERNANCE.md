# Lina 文档治理

本文定义重要文档的职责、事实来源和版本更新检查清单，避免代码、README、路线图和发布记录各自演进。

## 1. 重要文档清单

| 文档 | 职责 | 更新触发条件 |
| --- | --- | --- |
| `README.md` | 当前能力、工程证据、运行入口和参考文档导航 | 用户可见能力、指标、架构或文档入口变化 |
| `releaseNote.md` | 已发布版本的新增、修复、验证和限制 | 每次版本发布 |
| `docs/USER_GUIDE.md` | 当前版本实际可执行的操作 | API、页面、字段、启动方式或限制变化 |
| `docs/CODING_PLAN.md` | 未来阶段、依赖关系和验收标准 | 路线、优先级或阶段状态变化 |
| `docs/AGENT_ARCHITECTURE.md` | 当前模块边界、入口、数据契约、传输方向和架构债务 | 新入口、新领域模型、节点、适配器、持久化或数据边界变化 |
| `docs/DEVELOPMENT.md` | 开发环境、质量门禁和发布流程 | 工具、命令、CI 或协作流程变化 |
| `docs/RELEASE_TESTING_0.2.0.md` | 当前发布版本的逐步验收操作与预期结果 | 版本、入口、测试命令、指标或发布边界变化 |
| `docs/KNOWLEDGE_BASE.md` | 迭代日志和知识主题索引 | 每次可验收迭代完成 |
| `docs/MVP_IMPLEMENTATION.md` | MVP 当时的实现与复盘 | 历史记录原则上冻结，只补当前路线导航 |
| `docs/JOB_MONITORING.md` | 岗位监控规划与契约 | 监控设计或实现状态变化 |
| `docs/DATA_ANNOTATION.md` | 数据匿名化、标注和复核规范 | 数据 Schema、标签语义或隐私流程变化 |
| `docs/evaluations/JD_PARSER_BASELINE.md` | 已测量的解析指标与失败分析 | 数据集、解析器或指标结果变化 |

所有重要文档必须从 `README.md` 直接链接。`tests/test_documentation.py` 自动检查文件存在和链接完整性。

## 2. 事实来源

出现冲突时按以下顺序判断：

1. 代码、测试和可重复命令决定“实际行为”；
2. `releaseNote.md` 决定“某个已发布版本包含什么”；
3. `README.md` 与 `USER_GUIDE.md` 描述“用户现在能做什么”；
4. `CODING_PLAN.md` 描述“未来准备做什么”；
5. 迭代日志保留“当时发生了什么”，不使用新状态覆盖历史事实。

计划能力不得写成当前能力，手工验收不得写成自动化测试，合成数据不得写成真实数据。

## 3. 每次版本更新的统一 Review

发布前逐项检查：

1. 同步 `src/lina_agent/__init__.py`、`pyproject.toml` 和 `releaseNote.md` 的版本号。
2. 检查 README 的当前能力、测试数量、指标、截图、限制和参考文档链接。
3. 检查使用手册的启动命令、API、页面流程、错误处理和数据生命周期。
4. 更新 Coding Plan 的已完成状态、唯一下一步、依赖和验收标准。
5. 更新开发指南中的依赖、质量命令、迁移和发布流程。
6. 如评测数据或算法变化，重新生成评测报告，不手工猜测指标。
7. 如岗位监控、数据标注等设计状态变化，更新对应专题文档。
8. 新增本次迭代日志，并加入知识库索引。
9. 运行文档契约、Markdown 链接、Ruff、Pyright、pytest 和必要的浏览器验收。
10. 使用 `git diff` 检查是否误改历史日志、提交私有数据或留下过期数字。

纯文字修正不自动提升产品版本；新增用户能力、外部契约或重要数据迁移时才按发布规则递增版本。

## 4. Review 输出

每次重大版本的 release note 至少记录：

- 新增能力；
- 行为变化和兼容性；
- 修复的问题；
- 自动化与人工验证结果；
- 评测数据口径；
- 已知限制；
- 迁移或回滚方式。

迭代日志额外记录失败测试、根因、技术取舍、开发心得和面试表达。
