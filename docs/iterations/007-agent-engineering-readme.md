# 迭代 007：面向 Agent 工程评审的仓库叙事

> 日期：2026-08-23
> 类型：项目定位、技术表达与作品展示
> 状态：已完成

## 1. 用户问题

旧 README 虽然完整，但反复出现“目标 JD”“与目标岗位对应关系”“求职展示”和“面试素材”等措辞。面试官容易把仓库理解为针对某份职位描述临时拼装的作品，而不是由真实产品问题驱动、可持续演进的工程项目。

本次目标不是隐藏职业场景，而是把职业决策重新定位为 Agent 工程的第一个垂直试验场，并让面试官快速看到可验证的技术判断。

## 2. 初始假设与验证

**假设**：AI Agent 岗位面试官更关注边界设计、可靠性、评测和失败处理，而不是路线图中的框架名词数量。

**验证方式**：先重写 README，再由独立审查代理以高级 Agent 工程招聘经理身份核对代码、测试、评测和截图，指出任何夸大或定向包装痕迹。

审查结论：新叙事不再像为某家公司 JD 拼装，并能引发对确定性边界、评测口径和异步一致性的讨论；但首版仍存在 Agent 定位、证据范围和测试口径三类过度表达，随后全部收紧。

## 3. 叙事重构

### 3.1 从功能清单转为工程问题

README 首屏不再先列已实现和未实现功能，而是提出核心问题：在高风险决策中，如何让确定性规则、可追溯事实和用户控制共同构成 Agent 工作流的可靠基础。

### 3.2 从“已实现 Agent”转为“Agent 工程试验场”

当前版本没有 LLM、工具编排图或多轮会话，因此不直接宣称它已经是运行中的 AI Agent。准确定位为：

- evidence-grounded decision system；
- Agent engineering testbed；
- future Agent workflow 的 deterministic control plane。

这种表达不会降低项目价值，反而证明作者理解 Agent 与普通工作流之间的能力边界。

### 3.3 从技术名词转为可验证证据

README 优先展示：

- 硬条件由纯 Python 规则处理；
- 抽取值带原文与字符偏移；
- 抽取预览和保存分离；
- 35 个测试与 100% 分支覆盖；
- Pyright strict 与 Ruff；
- 6 个合成、人工标注案例；
- `10 TP / 0 FP / 6 FN`；
- 延迟响应浏览器场景和待自动化说明。

## 4. 可信度修正

独立审查发现并修复以下口径：

1. “every conclusion needs evidence” 超过当前实现范围。证据目前只绑定抽取预览，保存后的岗位和匹配报告尚未持久化证据引用，因此改为“extracted facts must remain traceable”。
2. 当前确定性版本不能直接称为完整 AI Agent，改为决策系统与 Agent 工程试验场。
3. stale-response 场景由手工 Playwright 验证，并非仓库内自动化回归测试，README 明确标注 automation pending。
4. 评测案例是合成人工标注数据，不应称为匿名真实数据；同时补充 TP、FP、FN，防止 Precision 1.0 被误读为生产效果。
5. 许可证尚未选择，公开仓库明确写为 All rights reserved。

## 6. 核心知识点

- 作品集 README 的第一任务是建立可信度，而不是覆盖全部需求文档。
- “尚未实现”的诚实边界比路线图中的框架名更能证明高级工程判断。
- 指标必须同时交代数据性质、样本量和混淆计数。
- 手工验收与自动回归测试必须使用不同口径。
- 截图应承担解释任务：一张建立产品认知，一张证明核心工程差异。
- 面试官愿意交流的原因通常是一个清晰、可争论的技术取舍，而不是“覆盖岗位要求”的表格。

## 7. 开发心得

1. 删除“目标 JD 对应关系”后，项目反而更像真实工程，也更容易讨论 Agent 架构。
2. 不应为了标题吸引力把确定性工作流提前称为完整 Agent。
3. 独立面试官审查最有价值的是验证主张是否被代码真正支撑。
4. README 不需要复制使用手册；快速开始、API 和详细文档入口足够。
5. 产品截图必须反复检查裁切、视口和信息密度，不能只确认文件已生成。

## 8. 验收标准

- README 不再出现“目标 JD”“目标岗位对应关系”“求职展示”或“面试素材”；
- 首屏明确项目的 Agent 工程问题与当前定位；
- 所有指标和能力主张可由代码、测试或评测报告核验；
- 当前能力与下一阶段能力明确分离；
- 两张截图存在、可读取且不包含个人隐私；
- README 所有相对链接有效；
- 独立 Agent 岗位面试官审查无高风险可信度问题。

## 9. 面试表达

### 30 秒表达

> Lina 不是为了展示我会调用模型 API，而是我用职业决策这个高风险场景研究 Agent 可靠性边界的项目。当前版本先完成确定性控制面：结构化领域模型、带字符偏移的证据抽取、人工确认边界、纯函数硬条件决策和离线评测。我刻意没有把它称为已经完成的自主 Agent，下一阶段才会加入结构化模型节点，并要求引用验证和同一套回归评测。这种推进顺序让我能区分问题来自规则、模型、上下文还是工作流。

### 值得讨论的问题

- 什么时候应该让模型推理，什么时候应该调用确定性工具？
- 证据文本匹配之外，如何评估引用是否真正支撑结论？
- 如何将当前应用服务升级为可恢复状态图，同时保持领域逻辑独立？
- 低召回、高精度是否是高风险自动预填产品的合理早期取舍？
