# 迭代 043：产品方向调整

> 日期：2026-09-28
> 类型：产品与路线重构
> 代码状态：不修改现有运行行为

## 1. 触发原因

0.2.25 已能可靠分析用户提供的简历和 JD，但仍要求用户先自行找到岗位。它更接近“可信匹配引擎”，没有完成用户最初期待的主动求职助理体验：通过对话理解目标，自动搜索公司官网，持续推送值得关注的岗位，并在审批后协助投递。

## 2. 决策

将产品主线从“继续增强 Run 审计界面”调整为：

1. 官方岗位发现；
2. 搜索结果收件箱与岗位对比；
3. 求职偏好和对话入口；
4. 订阅、调度和推送；
5. 公司、薪资和职业发展报告；
6. 简历、面试和投递看板；
7. 用户审批后的辅助投递。

Run 详情、检查点和恢复仍重要，但改为支撑跨来源、跨周期工作流的基础设施，不再单独作为近期产品目标。

## 3. 保留与复用

保留现有文档摄取、证据坐标、硬条件规则、技能与方向匹配、Top-K、gap、确定性 Reviewer、SQLite Repository、Snapshot/Diff、评测和浏览器测试。这些能力将作为搜索结果进入后的决策内核。

不再继续扩张两套平行候选人/岗位模型。新增搜索域从统一 `JobLead` 开始，并通过 mapper 接入现有 `CatalogJob`/匹配逻辑，逐步收敛旧结构。

## 4. 安全边界

- 搜索优先使用官方公开来源，不绕过登录、验证码、robots 或访问控制；
- 自动推送需要渠道级授权和可关闭订阅；
- 投递属于高风险外部写操作，每次提交前必须展示岗位、简历版本和字段预览；
- 不保存账号密码、验证码、Cookie 或会话 Token；
- 不伪造经历，不将未知资格标记为满足，不把来源失败解释为零岗位。

## 5. 第一实现切片

首个切片只完成一条可验收链路：

```text
类型化搜索请求
  -> 一个真实官方来源适配器
  -> JobLead 规范化
  -> 内容指纹与去重
  -> 复用当前匹配内核
  -> API 返回官方 URL、来源时间、匹配摘要和失败状态
```

首切片不加入定时器、LLM 对话或投递，以便先验证来源可靠性和领域契约。

## 6. 验收标准

- Fixture 覆盖成功、空结果、分页、限流、结构变化和超时；
- 同一岗位重复搜索不产生重复 `JobLead`；
- 来源失败具有独立状态，不能返回伪空列表；
- 每条结果具有官方 URL、来源 ID、获取时间和内容指纹；
- 可将规范化岗位送入现有匹配逻辑；
- 真实适配器遵守访问频率和来源条款；
- 默认测试不依赖公网，真实探针独立运行。

## 7. 后续顺序

1. 搜索结果 Inbox、收藏、忽略与对比；
2. 持久化 `SearchProfile` 和 `SavedSearch`；
3. 对话层把自然语言映射为已验证的搜索/比较工具；
4. 本地调度、变化检测和站内提醒；
5. 邮件等外部通知；
6. 公司与薪资证据源；
7. `ApplicationDraft`、审批和浏览器辅助填写；
8. 投递记录、面试准备与反馈闭环。

## 8. 行为准则

- 先证明来源数据可信，再优化推荐语义；
- 先做手动搜索，再做定时自动化；
- 先做站内通知，再做外部推送；
- 先做投递草稿和预览，再做真实提交；
- 对话只编排已注册工具，不能成为权限旁路；
- 用户价值优先级高于单独完善内部调试界面。
