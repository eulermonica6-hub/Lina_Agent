# 迭代 008：版本展示与发布记录

> 日期：2026-08-24
> 类型：版本治理与产品可识别性
> 状态：已完成

## 1. 用户问题

项目已有运行时版本和包版本，但用户无法从工作台直接识别当前版本，仓库也没有集中记录重大更新。版本号散落时，页面、API、包元数据和发布说明容易出现不一致。

本次目标：

- 当前版本明确记录为 `0.1.0`；
- 页面左上角展示版本号；
- 新增根目录 `releaseNote.md`；
- 规定下一次重大功能更新发布为 `0.1.1`；
- 用自动化测试阻止版本来源静默漂移。

## 2. 设计决策

### 2.1 页面不硬编码版本

运行时版本已定义在 `src/lina_agent/__init__.py`，并被 FastAPI 元数据和 `/health` 使用。首页改为模板响应，由后端将 `{{APP_VERSION}}` 替换为同一个 `__version__`。

这样页面无需再维护独立版本常量。更新运行时版本后，左上角徽标会自动变化。

### 2.2 三处版本契约

发布版本涉及三类信息：

- `src/lina_agent/__init__.py`：运行时与页面版本；
- `pyproject.toml`：构建和安装元数据版本；
- `releaseNote.md`：面向人类的版本记录。

`tests/test_versioning.py` 要求三者保持一致。release note 缺失当前版本标题或项目元数据未同步时，测试会失败。

### 2.3 当前阶段的递增规则

项目当前为 `0.1.0`。本阶段的重大功能更新按补丁位递增：下一版为 `0.1.1`，之后为 `0.1.2`。每次重大更新必须在推送前更新 release note，并让版本记录与代码进入同一 commit。

## 3. 测试驱动过程

先增加首页契约，要求响应包含 `v0.1.0` 且不泄露 `{{APP_VERSION}}`。旧实现没有版本徽标，测试失败。实现后测试转绿。

随后增加版本一致性测试。因为 `releaseNote.md` 尚不存在，首次运行得到 `FileNotFoundError`。创建发布记录后，测试验证运行时版本、项目元数据和 release note 一致。

## 4. 实现内容

- 页面品牌区域新增小型版本徽标；
- 首页由静态文件响应改为使用运行时版本渲染的 HTML 响应；
- CSS 资源版本升级，避免浏览器继续使用旧样式；
- 新增 `releaseNote.md`，记录 `0.1.0` 的能力、可靠性证据和已知限制；
- README 增加当前版本和发布记录入口；
- 开发指南增加重大更新发布清单；
- 新增版本一致性自动化测试。

## 5. 核心知识点

- 页面显示版本应复用运行时版本源，避免在 HTML 中重复硬编码。
- 包元数据和运行时常量仍是两个物理来源，需要测试约束一致性。
- release note 不只是功能清单，还应记录验证证据和已知限制。
- 发布记录必须在 push 前更新，并与对应代码放在同一个 commit。
- 版本徽标既帮助用户反馈问题，也便于截图、Demo 和故障记录关联具体版本。

## 6. 验收标准

- 首页左上角显示 `v0.1.0`；
- `/health` 继续返回 `0.1.0`；
- `pyproject.toml` 项目版本为 `0.1.0`；
- `releaseNote.md` 包含 `0.1.0` 记录和下一版规则；
- 首页响应不包含未替换模板占位符；
- 版本一致性测试和全量质量门禁通过；
- 真实桌面和移动视口均能正常展示版本徽标。

## 7. 下一次重大更新清单

发布 `0.1.1` 时：

1. 修改运行时版本与 `pyproject.toml`；
2. 在 `releaseNote.md` 顶部新增 `0.1.1`；
3. 更新其中的新增、修复、验证和限制；
4. 运行版本测试、全量测试与浏览器验收；
5. 在同一个 commit 中提交代码和发布记录，再 push。
