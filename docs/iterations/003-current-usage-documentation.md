# 迭代 003：当前使用说明与文档治理

> 日期：2026-08-23
> 类型：文档与产品边界迭代
> 状态：已完成

## 1. 用户问题

项目已经完成工作台、JD 硬条件解析和匹配，但使用信息散落在 README、开发指南和迭代日志中。README 同时描述当前能力和最终愿景，容易让使用者误认为对话、联网查询、简历优化和岗位监控已经可用。

本次目标是形成一份与运行代码一致的当前使用手册，并统一各类文档中的能力边界、启动命令和导航入口。

## 2. 验收标准

1. 新用户能从零完成安装、启动和一分钟匿名示例；
2. 用户能清楚区分当前可用、不可用和规划中的功能；
3. Web 与 API 两种用法都有可执行步骤；
4. 说明解析器支持范围、匹配原因和结果边界；
5. 说明内存数据、隐私约束和常见故障；
6. 文档中的端点与运行服务 OpenAPI 一致；
7. README、开发指南、路线图和知识库互相引用且职责明确。

## 3. 知识要点

### 3.1 产品愿景不能写成当前事实

“Lina 将支持公司调研”和“Lina 可以查询公司”代表完全不同的交付状态。文档必须用明确标签区分：

- **可用**：代码已实现，并有可复现操作或测试；
- **不可用**：当前版本没有这项能力；
- **规划中**：有设计或路线图，但不能承诺用户现在可以使用。

这也是 Agent 项目尤其需要注意的问题：架构图、Prompt 方案或工具清单不是运行能力的证据。

### 3.2 文档应按读者和任务分层

- README 回答“这是什么、现在能做什么、从哪里开始”；
- USER_GUIDE 回答“如何操作、输入什么、结果是什么意思”；
- DEVELOPMENT 回答“如何搭环境、开发和验证”；
- CODING_PLAN 回答“为什么这样演进、下一步做什么”；
- 迭代日志回答“过程发生了什么、学到了什么、如何面试表达”。

同一段完整说明不应复制到所有文件。README 保持短入口，细节由使用手册承载，减少后续漂移。

### 3.3 文档命令也需要运行验证

文档中的命令属于用户接口。仅凭代码阅读不能证明命令可执行。本次用真实服务验证：

- `GET /health` 返回服务名和版本；
- `POST /jobs/parse` 返回四类约束、证据和空警告；
- OpenAPI 实际包含 `/health`、`/profiles`、`/jobs/parse`、`/jobs`、`/matches`。

同时确认当前机器没有全局 `uv`。因此默认文档改用项目 `.venv` 中的 Python 和工具，`uv` 只作为可选安装方式。

### 3.4 结果边界必须随操作说明一起呈现

“硬条件通过”不能解释为“值得投递”或“会被录用”。当前结果只覆盖已录入的毕业年份、学历、经验和地点。技能语义、项目证据、偏好和成长空间尚未参与判断。

把限制放在结果解释旁边，比只在路线图末尾声明更能防止误用。

### 3.5 本地工具也需要隐私和安全说明

当前没有认证和持久化：

- 优点是数据不会发送给 LLM，服务停止后自动清空；
- 风险是不能恢复历史，也不适合暴露到公网；
- 真实简历必须继续留在 Git 忽略的私有目录。

“本地运行”并不自动等于安全，端口暴露、版本控制和日志仍需明确边界。

## 5. 发现的文档漂移

| 现象 | 风险 | 修正 |
| --- | --- | --- |
| 项目描述用现在时介绍完整 Agent 愿景 | 用户误认为对话和联网已实现 | 改为“正在演进”，显式列出不可用能力 |
| 每周监控、简历优化标题没有状态 | 设计文档被理解为产品功能 | 标记“规划中” |
| README 只演示创建岗位，没有解析 API | 最新增量无法被发现 | 增加 `/jobs/parse`，细节放入使用手册 |
| 文档要求全局 `uv` | 当前机器无法照文档执行 | 默认使用 `.venv`，uv 作为可选方案 |
| “硬条件通过”缺少语义边界 | 可能被当作综合匹配结论 | 在手册明确仅覆盖四类已录入门槛 |
| 缺少 `404`、`422` 和端口冲突说明 | 常见问题需要重新排查 | 增加故障处理章节 |

## 6. 开发心得

1. 文档应从运行事实反推，不应从路线图复制愿景。
2. 使用手册需要围绕用户任务组织，而不是围绕代码目录组织。
3. API 示例必须包含资源创建顺序和数据生命周期，否则 UUID 示例容易在重启后失效。
4. 环境依赖要以当前可执行路径为默认，不应假设全局工具存在。
5. 限制不是附录；它是正确理解结果的一部分。
6. 历史迭代日志应保留当时事实，当前状态由 README 和 USER_GUIDE 维护。

- 响应包含四类可回查原文证据且无警告；
- 全仓搜索未发现“Web 尚未实现”、旧 uv 启动方式等已知过时描述；
- 所有本地 Markdown 链接目标均存在；
- Ruff format、Ruff check 和 Pyright strict 全部通过；
- pytest：`26 passed`，246 条语句和 12 个分支达到 `100%` 覆盖率；
- `git diff --check` 通过。

链接检查首次使用包含负向前瞻的正则时，被 zsh 将 `!` 转义，导致 Python 正则编译失败。该失败属于验证脚本而非文档本身。改用“先提取全部链接、再按协议过滤”的实现后检查通过。经验是验证工具失败时必须区分被测对象失败和测试基础设施失败。

## 8. 遗留风险

- 尚未配置自动 Markdown 链接检查器；
- README 仍需同时承载项目愿景和当前能力，后续更新必须保持状态标签；
- Windows 原生虚拟环境命令与 Unix 不同，当前手册优先覆盖项目实际使用的 macOS 环境；
- API 示例使用固定 Fixture ID，只适用于创建 Fixture 后的同一服务进程。

### 高频追问

**如何防止文档再次过时？**
当前先通过每次迭代的完成清单和全仓漂移搜索控制；后续会把 OpenAPI 示例、Markdown 链接和关键启动命令加入 CI 文档测试。

**为什么把未实现功能写得这么明确？**
Agent 项目很容易把架构设计误当成产品能力。显式状态能够建立可信边界，也让后续每个增量有可验证的完成定义。
