# 迭代 009：代码现状与路线审计

> 日期：2026-08-24
> 类型：代码库总览、文档治理与实施路线校准
> 状态：已完成

## 1. 用户问题

随着 MVP、评测基线、README 和版本治理连续完成，代码真实能力与不同文档中的“当前状态”“下一步”开始出现漂移。需要重新以代码和测试为事实来源，回答三个问题：

1. Lina 当前到底实现了什么；
2. 哪些文档描述已经过期或超过代码保证；
3. 下一步应按什么依赖顺序实施。

## 2. 审计方法

- 枚举源码、测试、依赖、CI 和全部活跃文档；
- 对照领域模型、API、Repository、浏览器状态与评测代码；
- 搜索阶段、下一步、未实现、指标和版本等状态词；
- 将历史迭代日志视为当时事实，不用新状态覆盖旧记录；
- 用全量测试与 Markdown 链接检查验证调整。

## 3. 当前真实能力

当前 Lina 是确定性职业决策 MVP，不是自然语言 Agent。已经实现：

- 候选人画像和岗位领域模型；
- 内存 Repository 与应用服务；
- 候选人、岗位、JD 解析、硬条件匹配和健康检查 API；
- 中文 JD 明确硬条件规则抽取与原文字符偏移；
- 毕业年份、学历、经验和地点的确定性匹配；
- 浏览器工作台与异步旧响应保护；
- 6 例合成标注集的解析器离线评测；
- 36 个自动化测试与 100% 语句、分支覆盖率。

未实现：文件简历解析、候选人证据抽取、数据库、确认状态持久化、LLM Provider、语义匹配、状态图、自然语言对话、岗位监控、简历优化、学习规划和 Trace。

## 4. 发现的文档漂移

### 4.1 指标和阶段信息过期

README 与 release note 仍写 35 个测试，实际已增加版本一致性测试并达到 36 个。使用手册仍绑定 Phase 2 第一增量，开发指南仍把“扩展到至少 5 个 JD”写成下一步，但仓库已有 6 例合成评测集。

### 4.2 三套下一步互相冲突

- Coding Plan 指向补规则后文件解析；
- Development 指向补数据后文件解析；
- README 指向直接接 Provider 和结构化模型节点。

统一后以依赖顺序为准：真实数据、文件摄取、证据持久化、Provider、状态图、对话与上层功能。

### 4.3 人工确认的保证范围被写大

当前工作台确实要求用户检查后点击保存，但 API 和领域模型没有独立确认状态，也没有把抽取证据随岗位持久化。因此文档改为“界面把显式保存视为确认”，避免将 UI 流程描述成后端不变量。

### 4.4 跨周监控缺少持久化前置条件

内存 Repository 无法支持跨周快照、关闭检测和幂等运行。岗位监控文档增加“规划中”状态，并明确持久化与语义工作流依赖。

### 4.5 覆盖率声明没有 CI 强制

本地质量门禁要求 100% 覆盖率，但 CI 原命令只生成报告。CI 现已增加分支覆盖和 `--cov-fail-under=100`，让项目声明成为自动化不变量。

## 5. 校准后的实施路线

### 增量 1：匿名真实数据与标注

准备 8-10 个匿名真实 JD、至少 1 份匿名简历证据集，标注字段、原文跨度和人工匹配结论。验收包括隐私检查、Schema 校验和可重复基线。

### 增量 2：真实失败驱动的 JD 规则

只实现真实样例暴露出的高频明确表达，每条正例配误判反例。验收要求 Precision 不下降，Recall 或 Exact Match 有解释充分的提升。

### 增量 3：统一文件摄取

定义 `Document`、页码/段落/字符位置和解析错误；实现 Markdown、PDF、DOCX 到规范化文本。扫描 PDF 和损坏文件必须明确失败，不能伪装成空文档。

### 增量 4：证据与确认状态持久化

增加数据库迁移与 Repository 适配器，持久化文档快照、领域实体、证据和确认状态。重启后仍可追溯，未确认抽取不能进入匹配。

### 增量 5：LLM Provider 与结构化抽取

定义 Provider Protocol、Fake Provider、Pydantic 输出、超时、有限重试、预算和引用验证。Provider 不可用或输出非法时，确定性路径继续运行。

### 增量 6：候选人证据与语义匹配

从简历提取技能、经历和项目证据，输出命中、缺口、置信度与引用。硬条件仍由纯函数负责，Verifier 拒绝无来源的技能或经历。

### 增量 7：可恢复的类型化状态图

编排加载、硬规则、上下文构建、语义匹配、验证、人工确认和检查点。验收中包含中断恢复、幂等重试和节点级回归。

### 增量 8：对话与上层工作流

自然语言层只作为已注册工具和状态图的入口，不直接修改事实。岗位监控先实现 Fixture 来源、快照、指纹、变化检测和来源健康，再接语义排序；之后依次进入简历优化和学习规划。

## 6. 关键取舍

- 真实数据先于模型接入，否则无法判断提升来自规则、模型还是样本偏差。
- 文件解析拆为确定性文本摄取与概率性语义抽取，便于分别测试和替换。
- 持久化先于 LangGraph 检查点与跨周监控，否则“恢复”和“跨周”没有稳定状态。
- 对话后于类型化工具，不让自然语言入口成为绕过确认和校验的旁路。
- 岗位监控核心可与语义工作流部分并行，但跨周能力不能依赖进程内存。

## 8. 开发心得与面试表达

路线图也是系统接口：如果不同文档给出不同下一步，团队就无法判断依赖、验收和风险。此次审计没有新增业务功能，但把“想做什么”改成了“按什么前置条件、用什么失败信号、达到什么验收后再继续”。

30 秒表达：

> 我对 Lina 做了一次代码与路线审计，发现 MVP 已有 36 个测试和解析评测，但文档分别把文件解析、LLM 和真实数据写成下一步，人工确认的描述也超过后端保证。我以代码为事实来源，把 Phase 2 拆成真实基线、统一文件摄取、证据持久化和结构化模型抽取，并明确持久化先于跨周监控、类型化工作流先于聊天入口。同时让 CI 真正强制 100% 分支覆盖率，避免工程指标只停留在 README。
