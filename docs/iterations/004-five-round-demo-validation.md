## 1. 用户问题

用户要求自行连续测试 5 轮 Demo，确认功能是否正常并进行优化。重复运行同一个匿名示例只能证明一条路径，因此本次将五轮定义为五个能区分规则分支的真实浏览器场景。

目标不仅是检查返回结果，还要覆盖：

- JD 自动提取值是否正确；
- 每轮证据是否完整显示；
- 候选人与岗位是否真实保存；
- 匹配按钮状态是否正确；
- 重复操作是否会复用旧数据；
- 浏览器控制台是否报错；
- 桌面与手机布局是否溢出。

## 3. 发现的正确性缺陷

### 3.1 现象

完成一次保存和匹配后，点击“载入匿名示例”：

- 页面毕业年份从 `2027` 变成 `2028`；
- 状态仍显示“已保存”；
- 匹配按钮仍可点击；
- 前端保存的候选人 ID 仍指向旧的 `2027` 数据。

复现结果：

```json
{
  "before": {"year": "2027", "profileStatus": "已保存", "matchDisabled": false},
  "after": {"year": "2028", "profileStatus": "已保存", "matchDisabled": false},
  "bugReproduced": true
}
```

此时界面展示的是新数据，后端匹配的却是旧实体，属于状态一致性缺陷，而不只是文案问题。

### 3.2 根因

普通用户输入会触发表单的 `input` 事件，从而调用 `markUnsaved` 废弃旧 ID。匿名示例通过 JavaScript 直接设置 `.value`，程序化赋值不会自动触发 DOM `input` 事件，因此绕过了失效逻辑。

这是典型的“双路径状态更新”问题：手工输入路径维护了不变量，程序化填充路径没有维护相同不变量。

### 3.3 修复

建立统一的状态操作：

- `resetResult`：清空旧标题、摘要、原因和匹配步骤；
- `markUnsaved`：废弃对应 ID、更新状态、清空旧结论并禁用匹配；
- `resetWorkbench`：清空两个 ID、表单、证据、步骤、状态和结论。

“载入匿名示例”先调用 `resetWorkbench`，再写入示例值。新增“开始新一轮”按钮直接调用相同函数，避免再次产生一套独立重置逻辑。

## 4. 验证过程中的缓存问题

### 4.1 现象

首次验证修复时，HTML 已出现“开始新一轮”按钮，但点击无效，修改字段后旧结论也没有清空。编辑器诊断和首页契约均正常。

### 4.2 判断

同一页面同时出现“新 HTML + 旧 JavaScript”，说明浏览器缓存复用了 `/assets/app.js`。因此该次浏览器结果不能用于判断新状态代码是否正确。

### 4.3 修复

静态资源引用增加版本查询参数：

```html
<link rel="stylesheet" href="/assets/styles.css?v=2">
<script src="/assets/app.js?v=2" defer></script>
```

浏览器会将其视为新资源，避免热重载开发期间出现 HTML 与脚本版本错配。首页契约同步固定资源版本。

当前方案需要静态资源行为变化时手动更新版本号。未来引入正式前端构建后，应改为内容哈希文件名。

## 6. 知识要点

### 6.1 UI 展示状态与业务实体状态必须一致

表单字段只是草稿，Repository 中保存的是带 ID 的实体。只要草稿改变，旧 ID 就不能继续代表当前页面内容。可以把不变量写成：

```text
匹配按钮可用
=> candidateId 与当前候选人表单一致
且 jobId 与当前岗位表单一致
```

当前实现通过“任何修改立即废弃 ID”维护不变量。未来可改为内容指纹比较，但不能仅依赖状态文案。

### 6.2 程序化赋值不会自动模拟用户事件

设置 `input.value` 不会自然触发 `input` 或 `change`。测试数据加载、草稿恢复、导入文件和自动填充都必须显式调用状态更新函数，不能假设事件监听器会兜底。

### 6.3 端到端矩阵要覆盖分支，而不是重复次数

五次相同输入只能测稳定重复，无法证明四类失败原因映射正确。本次用一个成功分支加四个独立失败分支，让每一轮都具有区分能力。

### 6.4 测试基础设施也可能制造假失败

新 HTML 与旧 JS 混用时，浏览器行为不能代表当前源码。验证前需要确认资源版本、控制台和网络加载事实。不能因为测试失败就立刻修改业务逻辑。

### 6.5 重置操作是状态机的一部分

“开始新一轮”不是简单调用 `form.reset()`。它还必须清理实体 ID、证据、匹配结论、按钮状态和步骤状态。只重置可见输入会留下隐蔽的业务状态。

## 7. 开发心得

1. 成功路径全绿之后，最有价值的测试往往是连续使用和状态切换。
2. 前端正确性不能只看页面字段，必须同时检查背后的实体引用和按钮权限。
3. 复现数据应在修复前记录，避免只凭印象描述缺陷。
4. 公共状态操作应成为所有输入路径的唯一入口。
5. 缓存导致的混合版本会误导调试，静态资源应具备可追踪版本。
6. 手工端到端测试应逐步沉淀为自动化浏览器回归，但当前仓库尚未引入 Playwright 测试依赖。

## 8. 产品与视觉验收

- 桌面视口：重置操作可见，结果与证据区域无横向溢出；
- 手机视口：两个首屏操作纵向排列，文本和按钮无重叠；
- 手机视口文档宽度与客户端宽度一致；
- 重置后匹配按钮保持禁用；
- 两次五轮测试浏览器控制台均无错误。

## 9. 遗留风险

- 五轮浏览器测试目前由开发工具执行，尚未进入 CI；
- 静态资源版本号需要人工递增；
- 内存 Repository 会保留每轮创建的数据直到服务重启，没有删除接口；
- 当前没有多标签页并发状态同步；
- 没有测试网络超时、服务中断和 API 返回 422 时的完整 UI 恢复行为。

### 高频追问

**为什么单元测试没有发现这个问题？**
领域规则测试只验证相同输入的计算结果，缺陷发生在浏览器草稿和后端实体 ID 的生命周期之间，需要端到端状态切换才能暴露。

**为什么不直接每次匹配都重新提交表单？**
当前 API 契约把创建实体和运行匹配分开。短期通过修改即废弃 ID 保持契约一致；未来可以增加“分析草稿”用例，一次请求完成校验、暂存和匹配。

**如何把五轮测试加入 CI？**
引入 Playwright 测试依赖和固定浏览器版本，启动测试服务后用参数化场景运行同一工作台流程，并保存失败截图、控制台和网络日志。
